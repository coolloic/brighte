Resolvers, Zod validation

DataLoader, Sequelize

Postgres 17

leads, service_types, lead_service_types, users

Umzug migrations

The API sits on a private network, reachable only from the web server. The admin's token stays in an httpOnly cookie, and rate limits see the real visitor.

Every admin page and action calls requireAdmin(), which asks the API who the token belongs to; the cookie alone proves nothing. Validation runs twice: in the browser for instant feedback, and in the API as the source of truth.

Non-functional · Data model

Service types live in a table

Rejected

Enum

A new type needs a migration and a deploy. Postgres can't drop an enum value, and there's nowhere for a label or active flag.

Chosen

Join table

Foreign keys protect every interest. The service filter is a plain indexed join, and a DataLoader avoids N+1.

Rejected

JSON column

Quickest to write, but no foreign key: nothing stops "delivry". Filtering needs a GIN index.

A new service is an INSERT; a retired one is active = false. Existing leads keep their history.

Lead ids are UUID v7: not guessable, don't reveal sign-up volume, and time-ordered so inserts append to the index. The cost of the join table: register writes two tables in one transaction.

Non-functional considerations

Decided, and covered by tests

Idempotency

Unique email in the database; a duplicate gets CONFLICT, never a merge.

Validation

Shared Zod rules: the browser checks first, the API decides.

Security

Deny by default, per-IP limits with backoff, nonce CSP.

Performance

No N+1, trigram search indexes, a bounded DB pool.

Resilience

Instant confirmation, reconciled; input kept through errors and reloads; works without JavaScript.

Observability

JSON logs with request ids, audit events, live and ready checks.

Accessibility

WCAG 2.1 AA, AAA text contrast, axe on every story.

Migrations

Umzug steps with up and down; the ORM never alters the schema.

Register doesn't merge into or return an existing lead: that would hand anyone who knows an email that person's details. Rate limits: register 5 a minute, login 10, doubling backoff up to 15 minutes. Statements time out after 5 seconds.

Reliability · TODO

Only the screen is fire and forget

1 · Build first

Saved, but the answer is lost

Today: a timeout says "couldn't send"; Try again then says "already registered".

Why: two wrong messages, and retries can't be automatic.

Fix: an idempotency key per submission, then automatic retries.

2 · Client side

The browser never sends it

Today: tab closed in the second after "Thanks": lost.

Why: a confirmation for a registration that doesn't exist.

Fix: keep it in localStorage until confirmed; resend on the next visit.

3 · Matters most

The API or Postgres is down

Today: "couldn't send", details kept; the visitor must come back.

Why: some visitors won't; Postgres can't cover its own outage.

Fix: Next publishes to Kafka when the API fails; an API consumer saves it later.

The confirmation shows before the server answers (useOptimistic), but it stays only once Postgres has committed the lead; anything else withdraws it with the reason and what was typed. So nothing the server accepted is lost. These are the gaps left. Gap 1 comes first because gaps 2 and 3 both need retries to be safe. For gap 3, Kafka runs with acks=all and an idempotent producer; the consumer commits its offset after the database commit, treats a replayed CONFLICT as done and sends validation failures to a dead-letter topic. Still to decide: queue only as a fallback, which keeps the duplicate-email and rate-limit feedback, or every registration. Details and checklist in docs/architecture.md.

OIDC; migrates with the CI secret

Cognito user pool

Groups ADMIN and USER become roles. Web app client: code flow with PKCE.

ElastiCache Redis

Secrets Manager

Per-role DB secrets

Browsers reach only the edge. Web, API, Redis and the database sit in private subnets; only the BFF can call the API.

Top row is the request path. The BFF signs admins in through Cognito and keeps their sessions in Redis. The API verifies Cognito tokens against the user pool's JWKS and uses Redis for shared rate-limit counters. Each service reads its own database secret from Secrets Manager; CI runs migrations with a separate, more privileged one. Pages carry a per-request CSP nonce, so CloudFront caches only /_next/static.

Cloud-native on AWS · Identity

Cognito signs people in; the API decides

1

Sign in

/admin redirects to Cognito's managed login: authorisation code with PKCE.

2

Session

The BFF swaps the code using its client secret. Tokens stay in Redis; the browser gets an opaque httpOnly cookie.

3

Call the API

The API verifies the access token against Cognito's JWKS and maps cognito:groups to ADMIN or USER.

4

Sign out

The BFF deletes the session and revokes the refresh token: sessions become revocable.

Cognito setup

  • User pool: MFA and threat protection for admins
  • Groups ADMIN and USER feed the existing @Roles guard
  • App client web-bff: confidential, code flow
  • App client ci-smoke: client credentials, own scope
  • Access token 30 min, refresh token 8 h
  • Admins created in Cognito, not by createUser
Token lifetimes match today's sessions: 8 hours at most, and the BFF expires a session in Redis after 30 minutes idle. Moving to Cognito retires the API's login mutation, password hashing and the users' password column; the deny-by-default AuthGuard and @Roles stay, with the JWT strategy switched to Cognito's keys (for example aws-jwt-verify). Rate limiting on login moves to Cognito and WAF.

Recommendation · BFF

Keep the BFF in Next.js

Yes to a BFF as a guard, but it already exists: the Next.js server. Make it the first guard and keep the API as the final one.

BFF: coarse, user-facing

  • Session present and not idle
  • ADMIN group before rendering /admin
  • Holds the tokens; the browser never does
  • Same-origin Server Actions, nonce CSP
  • Forwards the visitor IP for rate limits

API: authoritative

  • Verifies signature, expiry, audience
  • @Roles on every field, deny by default
  • Zod validation, rate limits in Redis
  • Reachable only from the BFF's security group
  • Never trusts the BFF's own checks

Not recommended: a separate BFF service or API Gateway in front. One more hop and deploy, no new control.

Revisit API Gateway if third parties or a mobile app need to call the API directly; then it adds usage plans, API keys and a Cognito authorizer. Until then the Next.js server already does what a BFF is for: it tailors data for the pages and keeps tokens off the client.

Cloud-native on AWS · Database access

One secret per job, least privilege

SecretDatabase roleCanUsed by
Appbrighte_appRead and write rows; no DDLAPI tasks
CIbrighte_migratorOwns the schema; migrationsCI migration task
Read-onlybrighte_readonlySELECT only, on the replicaReporting, support
AdminRDS master userEverything; break-glassNo one, day to day

Each ECS task role can read only its own secret; the CI secret only through GitHub's OIDC role. Secrets rotate automatically, and RDS Proxy holds the app and read-only ones.

The migrator role owns the tables and the SequelizeMeta history, and grants the app role access with ALTER DEFAULT PRIVILEGES, so new tables from later migrations are covered. A leaked app secret can't drop or alter tables; a leaked read-only secret can't write. Today the API uses one DATABASE_URL for both running and migrating.

Six steps to get there

Dockerfiles for web and API; Next.js standalone output; images in ECR.

Infrastructure as code

CDK in TypeScript: VPC, CloudFront, ALB, ECS, RDS Proxy, ElastiCache, Cognito.

3

Least-privilege database

App, CI and read-only roles, one rotated secret each, readable only by its own task.

4

Auth on Cognito

The BFF runs the code flow; the API verifies Cognito tokens; groups become roles.

5

Redis cache layer

Sessions, the service-type cache and rate-limit counters, shared by every task.

6

Pipeline and operations

GitHub OIDC, migrate with the CI secret, roll out; alarms on errors and rate_limit.blocked; autoscaling.

Other settings: WEB_TRUST_PROXY=2 (CloudFront and the ALB sit in front of the web), TRUST_PROXY=1 on the API, SITE_URL and WEB_ORIGIN set to the public HTTPS address. Keep instances times DB_POOL_MAX under the database's connection limit, or let RDS Proxy absorb it.

A new service is a row, not a deploy.

Next: CI on every pull request, shared rate limits, and a CDK stack for AWS.

Built to change: the data model, validation and security choices keep the app easy to adapt, and the move to AWS is mostly infrastructure rather than code.

Demo · Form errors on mobile

Every error says what to do

Invalid input: caught in the browser

Duplicate email: the API's CONFLICT

Rate limited: a live countdown

Wrong password: no hint which

Invalid input is checked with the shared rules before anything is sent, so typos never count against the rate limit. The duplicate message sits on the email field and keeps everything typed. The sixth register attempt in a minute gets TOO_MANY_REQUESTS; the countdown comes from the API's retryAfter, and repeat offenders wait twice as long each time. Sign-in never says whether the email exists.

Demo · Failures on mobile

Failing politely, with a way out

Connection lost: details kept

API down: a message and Try again

404: branded, with a way home

Error boundary: no internal details

Connection lost mid-submit: the form stays with everything typed, and Try again sends it once back online. API down: the register page explains instead of showing a broken form. The 404 page covers any unknown URL. The error boundary (app/error.tsx) catches failures such as the admin dashboard when the API can't be reached: it returns 500, shows no stack or connection details, and Try again fetches the page again.

Demo · Operability

Health, request ids, bounded pool

Live vs ready

Live never touches the database; ready returns 503 if Postgres is slow.

Request ids

A caller's id is kept and echoed; otherwise the API makes one.

Bounded pool

Named brighte-api; at most 10, idle ones close after 10 s.

Captured from the API running with NODE_ENV=production. Liveness doesn't touch the database, so a database outage doesn't get the API restarted; readiness takes it out of the load balancer instead. The web server can pass its own request id so both sides log the same one. Statements past 5 seconds are cancelled.

Demo · Operability

Logs a collector can alert on

One JSON object per line on stdout: one line per GraphQL operation with its name, duration, caller and error codes, plus security events with an event field to alert on, such as auth.login_failed and rate_limit.blocked. The first line carries the request id from the previous slide. Variables, headers, tokens and emails are never logged. Hostname and pid were removed from these lines for the slide.
