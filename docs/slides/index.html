The API sits on a private network, reachable only from the web server. The admin's token stays in an httpOnly cookie, and rate limits see the real visitor.

Every admin page and action calls requireAdmin(), which asks the API who the token belongs to; the cookie alone proves nothing. Validation runs twice: in the browser for instant feedback, and in the API as the source of truth.

Non-functional · Data model

Service types live in a table

Rejected

Enum

A new type needs a migration and a deploy. Postgres can't drop an enum value, and there's nowhere for a label or active flag.

Chosen

Join table

Foreign keys protect every interest. The service filter is a plain indexed join, and a DataLoader avoids N+1.

Rejected

JSON column

Quickest to write, but no foreign key: nothing stops "delivry". Filtering needs a GIN index.

A new service is an INSERT; a retired one is active = false. Existing leads keep their history.

Lead ids are UUID v7: not guessable, don't reveal sign-up volume, and time-ordered so inserts append to the index. The cost of the join table: register writes two tables in one transaction.

1 · Performance · found by the test

Admin search read the whole table: fixed

42 → 1,265

searches per second, same search terms

242 → 7 ms

median response, 10 concurrent admins

0

pool timeouts after the fix (7 before, at 200)

Cause

Search is one OR across name, email, postcode and mobile. Postgres uses the trigram indexes only if every branch has an index; postcode and mobile had none, so every search scanned all rows, twice (page and count).

Fix · migration, with a test

A prefix index on postcode and a trigram index on mobile, so Postgres combines all four (BitmapOr). An e2e test checks the plan; one search went from 49 ms to 0.34 ms.

At 200 concurrent admins the slow search filled all 10 pooled connections and 7 requests waited past the 5-second acquire timeout: the bounded pool failed fast instead of queueing forever, as designed. The fix is the add-leads-postcode-mobile-indexes migration. The after figures come from the same load test against a fresh database built by the migrations, with a warm cache (the very first run, on a cold cache, managed 716 a second). The e2e test turns plain scans off and checks that the search's plan uses all four indexes, so a new search column without an index fails the build. A search that matches most rows (like a common mobile prefix) still scans, which is the right plan for Postgres.

3 · Reliability and availability

Fail fast, keep what the visitor typed

In place

  • Instant confirmation, kept only once Postgres commits
  • Typed details kept through errors and reloads
  • Bounded pool: 10 connections, 5 s to get one, 5 s per statement; the load test saw it fail fast
  • Live check never touches the database; ready returns 503, so a balancer drains the instance
  • Web waits 10 s for the API, then shows Try again
  • Rate limits with backoff keep floods off the database

TODO

  • Queue registrations while the API or Postgres is down (next slide)
  • Idempotency key, then automatic retries
  • Graceful shutdown: finish requests in flight on deploy
  • Health endpoint for the web tier
  • Uptime target and alarms, set with the AWS move (Multi-AZ)
Availability targets such as 99.9% belong to the infrastructure: two or more tasks across availability zones, RDS Multi-AZ, health checks on the load balancer. The application's part is to fail fast and visibly, never lose what the visitor typed, and let the balancer take a sick instance out of rotation. Graceful shutdown means enableShutdownHooks in Nest and readiness answering 503 while draining.

3 · Reliability · outage queue

SQS fits this; Kafka if events fan out

Amazon SQSKafka
Holds messagesUp to 14 days (default 4)Retention by time or size (default 7 days); unlimited is possible but must be configured
A failed saveComes back after the visibility timeout; to a dead-letter queue after N triesStays until the consumer commits its offset; dead-letter topic by convention
DuplicatesFIFO: deduplicated by id for 5 minutesIdempotent producer; consumers still dedupe
To runFully managed, pay per requestA cluster (or MSK) to size, patch and watch
Best forOne consumer, modest volumeMany consumers, replay, event streams

Plan: SQS FIFO. Deduplication id: a hash of all the details, so a corrected submission still goes through (the email alone would drop it). Group id: a hash of the email, so its submissions stay in order. The worker is idempotent anyway.

Correction to a common belief: Kafka doesn't keep messages forever by default. Topics have a retention time or size, 7 days by default; infinite retention has to be set, and tiered storage makes it affordable. Delivery is guaranteed when producers use acks=all with replication factor 3 and min.insync.replicas 2, and consumers commit only after the database commit. SQS gives the same outcome for one consumer with nothing to operate: a message that fails comes back after its visibility timeout and moves to a dead-letter queue after maxReceiveCount. Both hashes are HMACs with a secret, computed on the Next server, so no email appears in queue metadata. The 5-minute deduplication window only catches quick repeats; the submission_id stored on the lead makes a replay days later a success too. If registrations later feed a CRM, emails and analytics, Kafka (or SNS fan-out to several SQS queues) becomes worth it.

Reliability · TODO

Only the screen is fire and forget

1 · Build first

Saved, but the answer is lost

Today: a timeout says "couldn't send"; Try again then says "already registered".

Why: two wrong messages, and retries can't be automatic.

Fix: a key hashed from the details on the server, then automatic retries.

2 · Client side

The browser never sends it

Today: tab closed in the second after "Thanks": lost.

Why: a confirmation for a registration that doesn't exist.

Fix: keep it in localStorage until confirmed; resend on the next visit.

3 · Matters most

The API or Postgres is down

Today: "couldn't send", details kept; the visitor must come back.

Why: some visitors won't; Postgres can't cover its own outage.

Fix: the web queues it (SQS) when the API fails; a worker saves it later.

The confirmation shows before the server answers (useOptimistic), but it stays only once Postgres has committed the lead; anything else withdraws it with the reason and what was typed. So nothing the server accepted is lost. These are the gaps left. Gap 1 comes first because gaps 2 and 3 both need retries to be safe. The idempotency key is HMAC-SHA256 of the normalised details (email lowercased, mobile as digits, services sorted), computed on the Next server with a secret: identical details always give the same key, so retries, the resend and the queue agree with nothing stored, while a corrected submission gets a new key and is told the email is taken instead of being dropped. Never computed in the browser, where the key would be public and the hash a guessable fingerprint of personal data. For gap 3, an SQS FIFO queue with the submission id as its deduplication id: a failed save comes back after the visibility timeout and goes to a dead-letter queue after a few tries; a replayed CONFLICT counts as done. Kafka works too, and is worth it once registrations feed several systems. Still to decide: queue only as a fallback, which keeps the duplicate-email and rate-limit feedback, or every registration. Details and checklist in docs/architecture.md.

Cloud-native on AWS · Identity

Cognito signs people in; the API decides

1

Sign in

/admin redirects to Cognito's managed login: authorisation code with PKCE.

2

Session

The BFF swaps the code using its client secret. Tokens stay in Redis; the browser gets an opaque httpOnly cookie.

3

Call the API

The API verifies the access token against Cognito's JWKS and maps cognito:groups to ADMIN or USER.

4

Sign out

The BFF deletes the session and revokes the refresh token: sessions become revocable.

Cognito setup

  • User pool: MFA and threat protection for admins
  • Groups ADMIN and USER feed the existing @Roles guard
  • App client web-bff: confidential, code flow
  • App client ci-smoke: client credentials, own scope
  • Access token 30 min, refresh token 8 h
  • Admins created in Cognito, not by createUser
Token lifetimes match today's sessions: 8 hours at most, and the BFF expires a session in Redis after 30 minutes idle. Moving to Cognito retires the API's login mutation, password hashing and the users' password column; the deny-by-default AuthGuard and @Roles stay, with the JWT strategy switched to Cognito's keys (for example aws-jwt-verify). Rate limiting on login moves to Cognito and WAF.

Recommendation · BFF

Keep the BFF in Next.js

Yes to a BFF as a guard, but it already exists: the Next.js server. Make it the first guard and keep the API as the final one.

BFF: coarse, user-facing

  • Session present and not idle
  • ADMIN group before rendering /admin
  • Holds the tokens; the browser never does
  • Same-origin Server Actions, nonce CSP
  • Forwards the visitor IP for rate limits

API: authoritative

  • Verifies signature, expiry, audience
  • @Roles on every field, deny by default
  • Zod validation, rate limits in Redis
  • Reachable only from the BFF's security group
  • Never trusts the BFF's own checks

Not recommended: a separate BFF service or API Gateway in front. One more hop and deploy, no new control.

Revisit API Gateway if third parties or a mobile app need to call the API directly; then it adds usage plans, API keys and a Cognito authorizer. Until then the Next.js server already does what a BFF is for: it tailors data for the pages and keeps tokens off the client.

Each ECS task role can read only its own secret; the CI secret only through GitHub's OIDC role. Secrets rotate automatically, and RDS Proxy holds the app and read-only ones.

Invalid input: caught in the browser

Duplicate email: the API's CONFLICT

Rate limited: a live countdown

Wrong password: no hint which

Invalid input is checked with the shared rules before anything is sent, so typos never count against the rate limit. The duplicate message sits on the email field and keeps everything typed. The sixth register attempt in a minute gets TOO_MANY_REQUESTS; the countdown comes from the API's retryAfter, and repeat offenders wait twice as long each time. Sign-in never says whether the email exists.

Demo · Failures on mobile

Failing politely, with a way out

Connection lost: details kept

API down: a message and Try again

404: branded, with a way home

Error boundary: no internal details

Connection lost mid-submit: the form stays with everything typed, and Try again sends it once back online. API down: the register page explains instead of showing a broken form. The 404 page covers any unknown URL. The error boundary (app/error.tsx) catches failures such as the admin dashboard when the API can't be reached: it returns 500, shows no stack or connection details, and Try again fetches the page again.

Bounded pool

Named brighte-api; at most 10, idle ones close after 10 s.

Captured from the API running with NODE_ENV=production. Liveness doesn't touch the database, so a database outage doesn't get the API restarted; readiness takes it out of the load balancer instead. The web server can pass its own request id so both sides log the same one. Statements past 5 seconds are cancelled.

Logs a collector can alert on

One JSON object per line on stdout: one line per GraphQL operation with its name, duration, caller and error codes, plus security events with an event field to alert on, such as auth.login_failed and rate_limit.blocked. The first line carries the request id from the previous slide. Variables, headers, tokens and emails are never logged. Hostname and pid were removed from these lines for the slide.
